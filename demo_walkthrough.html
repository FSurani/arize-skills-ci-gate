Gating AI-Authored Skills in CI

A worked example for an internal skills registry: replace an inline evals.json + Sentry scan with one reusable, Arize-native CI gate — covering both verifiable skills (deterministic checks) and non-verifiable ones (LLM judge), with every run recorded in Arize.

What we're building

One reusable gate, standardized on Arize

Teams author many skills across the registry — API helpers, user-story writers, and more. Today they're gated in CI by an inline three-phase evals.json plus a Sentry skill-scan. This reference folds all of that into a single GitHub Actions workflow that runs the same phases on Arize AX and blocks the PR on any breach.

Arize is the system of record: the gate creates an experiment per skill version, lets Arize's evaluators score it server-side, then reads those scores back to decide pass/fail. The experiment history in Arize is the skill's version history.

The skills

Two examples — because the registry is heterogeneous

A gate is only useful if it covers every kind of skill. So this reference carries one of each: a verifiable API skill (there's a right answer) and a non-verifiable writing skill (quality is judged, not checked).

Verifiable

api-helper

Call the internal Orders service correctly — auth header, pagination, retries, error handling. Correctness is checked deterministically against a mock API.

Shipped in two variants to show description tuning: a broad one (over-triggers) and a tight one with a worked example (clean).

variant_b/SKILL.md — the tight version 
---
name: api-helper
description: Call the internal Orders service, and ONLY that service …
  Do NOT use for generic HTTP, third-party APIs, CSV parsing, or unrelated
  pagination/error-handling questions.
---

# Orders Service Helper (internal)

## Connection & auth
- Base URL: the ORDERS_API_BASE environment variable.
- Auth: header X-Org-Token: <ORDERS_API_TOKEN>.
  Do NOT use Authorization: Bearer — the service returns 401.

## Pagination (required for "all orders")
GET /orders returns {"data":[…], "next_cursor": …}. Loop on ?cursor=
until next_cursor is null. Do not stop after page one.

## Retries
On 503/429, honor Retry-After and retry once.

## Worked example — count all orders (Python) … [full code in repo]
variant_a/SKILL.md — the broad version (intentionally worse) 
---
name: api-helper
description: Helps you work with APIs and web services — making HTTP
  requests, handling authentication, following pagination, processing
  orders … Use this whenever a task involves calling an API.
---

# API Helper
Use this skill to talk to our backend services.
The base URL is in ORDERS_API_BASE. Send an authentication header.
Some list endpoints are paginated. Handle errors as they come up.

# Broad description → fires on unrelated prompts (trigger false-positives);
# terse body, no auth/pagination specifics → lower task pass rate.

Non-verifiable

story-writer

Turn a feature request into INVEST-style user stories following the team's template. There's no single correct output — quality is judged against a rubric by an LLM.

This is the case an assertion-based gate can't handle — and the reason the framework needs a judge path.

story-writer/SKILL.md 
---
name: story-writer
description: Write user stories for the team's backlog following the internal
  INVEST-based template — a user-voice statement plus testable
  acceptance criteria.
---

## Output template
**Story:** As a <specific role>, I want <capability> so that <benefit>.
**Acceptance Criteria:** 2–5 testable Given/When/Then outcomes.

## Quality bar (INVEST)
Independent · Negotiable · Valuable · Estimable · Small · Testable
- Use a SPECIFIC role (not "user"). Split epics into multiple stories.
- Do not invent requirements that weren't stated.

The evals

What the gate checks

The three phases from evals.json, plus efficiency, expressed as evaluators. The functional phase has two interchangeable paths that emit the same result shape — so the gate doesn't care whether a skill is verifiable.

EvalPhaseWhat it checksHowIn Arize
Eval 01 · structural + securityFrontmatter, referenced files, no absolute paths; prompt-injection scan, embedded secrets, unsafe bundled scriptscodein-gate (pre-experiment)
Eval 12 · triggerDid the skill load exactly when it should? False-positive / false-negative ratescodecc-eval1-trigger
Eval 23 · functionalVerifiable: deterministic verifier vs a mock API. Non-verifiable: rubric LLM judge (good/bad + explanation)code or LLMcc-eval2-verifier · cc-eval2-rubric
Eval 4efficiencyTokens / turns per case against a budget — the tie-breakercodecc-eval4-efficiency

Eval 1, 2 and 4 are Arize evaluators (created once, referenced by id, run server-side). Eval 0 runs first, in-gate, and short-circuits the pipeline on failure.

Security gate

The bad skill bounces at the door

Eval 0 is where the Sentry scan standardizes. A skill with a planted prompt-injection and a data-exfiltration script fails immediately, before any model runs:

Eval 0 — a deliberately malicious skill
[no_prompt_injection] instruction-override phrasing; instructs the agent to
   hide actions from the user; instructs reading credentials/secrets;
   instructs sending data to an external URL
[no_embedded_secrets] Anthropic-style API key
[bundled_scripts_safe] scripts/beacon.py: undeclared network call;
   reads a credential/system file; reads a third-party secret from env

VERDICT: FAIL — bounced at the door (exit 1; nothing runs)

The Eval 0 code

Each finding above comes from a small, transparent pattern set — no black box. This is the whole detection surface (from gates/eval0_structural.py):

gates/eval0_structural.py — the security signatures 
# prompt-injection / instruction-override aimed at the agent
INJECTION_PATTERNS = [
  (r"ignore\s+(all\s+)?(previous|prior|above)\s+instructions", "instruction-override"),
  (r"do\s+not\s+(tell|inform)\s+the\s+user",                   "hide actions from the user"),
  (r"\bexfiltrat",                                              "exfiltration language"),
  (r"(read|cat|open)\b.*(credential|\.aws|\.ssh|id_rsa|/etc/passwd)", "reads secrets"),
  (r"\b(AWS_SECRET_ACCESS_KEY|ANTHROPIC_API_KEY|GITHUB_TOKEN)\b", "3rd-party credential"),
  (r"(send|post|upload|beacon).*(https?://)",                  "sends data to external URL"),
]
# embedded secrets
SECRET_PATTERNS = [ (r"sk-ant-[A-Za-z0-9\-]{20,}", "Anthropic key"),
                    (r"AKIA[0-9A-Z]{16}", "AWS key"), (r"ghp_[A-Za-z0-9]{20,}", "GitHub PAT"), … ]
# bundled scripts: network calls not declared in the description, or cred reads
NET_PATTERNS  = [ (r"requests\.(get|post)|urllib\.request|socket\.socket", "network call"), … ]
CRED_PATTERNS = [ (r"os\.environ\[.(AWS_SECRET_ACCESS_KEY|ANTHROPIC_API_KEY)", "reads a secret from env"), … ]

The CI gate

How to do it — the reusable workflow

Two steps: provision Arize once (create the evaluators + datasets in the Eval Hub), then gate on every change. Both are tiny; drop them into any agent repo, secrets are org-level, and Arize is the system of record.

experiments/setup.py — provision Arize (run once) 
import eval_hub as hub

evaluators = hub.ensure_evaluators()        # create the 4 evals in the Eval Hub (idempotent)
for skill in ("api-helper", "story-writer"):
    hub.ensure_dataset(skill)               # one stable cc-<skill> dataset each
.github/workflows/skill-gate.yml — copy into any repo 
name: skill-gate
on:
  workflow_call:
    inputs:
      skill: { type: string, default: "" }   # empty = auto-detect changed skills
      mock:  { type: boolean, default: false }
    secrets:
      ARIZE_API_KEY:           { required: true }
      ARIZE_SPACE_ID:          { required: true }
      ARIZE_AI_INTEGRATION_ID: { required: false } # for the LLM rubric judge
      ANTHROPIC_API_KEY:       { required: false } # absent → gate runs in --mock

jobs:
  gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.11" }
      - run: pip install -r requirements.txt   # incl. arize-ax-cli 0.27
      - run: ax profiles create arize-ci --api-key "$ARIZE_API_KEY" --auth-method api-key
      - run: python experiments/setup.py       # provision evaluators + datasets (idempotent)
      - run: python ci/gate.py --skill "${{ matrix.skill }}"  # eval0 → harness → Arize → call
ci/thresholds.yaml — per-skill gate thresholds 
default:
  eval0: all_checks_pass          # structural + security must fully pass
  trigger_fp_rate_max: 0.10       # hard-negatives that wrongly triggered
  trigger_fn_rate_max: 0.10
  functional_pass_rate_min: 0.80  # Eval 2 pass@1 over task/edge cases
  max_tokens_per_case_p50: 30000
skills:
  api-helper: {}
  story-writer: { functional_pass_rate_min: 0.80 }  # rubric judge, same bar
gate.py eval_hub.py (the evals) setup.py skill-gate.yml thresholds.yaml

The richness lives in eval_hub.py (the evaluators); the pipeline in gate.py is ~5 steps. Full source in FSurani/arize-skills-ci-gate. Links above open each file on GitHub.

Architecture & roadmap

Beyond the CI gate

Reusable CI

One workflow, org-wide

Single skill-gate.yml; AX CLI manages datasets / experiments / evaluators; experiments append-only, never deleted. Thresholds per-skill.

Security

Static now, runtime next

Static injection scan as a CI hard gate today; layer a dedicated scanner and Arize Guardrails / online-evals for live traffic.

Tracing

Default-on at the utils layer

The Coding-Harness-Tracing plugin via settings.json → every agent from your agent platforms is traced automatically, no per-agent code.

Data masking

Flags now, redaction hook next

Coarse ARIZE_LOG_* flags today; for field-level PII/secret masking, an OTel span-processor in the platform utils library — centralized, default-on.
